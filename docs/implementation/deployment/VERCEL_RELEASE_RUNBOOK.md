## Quotas, backups and rollback

Global database budgets: 60 guest entries/hour, 1,200 API requests/minute, 12,000/hour; 50 active guests, 2 sessions/guest, 200 mutations/guest, 30 review revisions. Guest TTL two hours. DB transactions/advisory lock serialize demo mutations; not a high-throughput claim. HTTP 429 is intentional. Extended regression runs hit the guest-entry budget; wait for the next clock-hour window rather than clearing it or weakening limits. Cloud browser assertions allow 30 seconds; an observed auth request took 9.48 seconds. No uptime/latency SLA or DDoS guarantee.

`python -m tools.backup_neon_demo` makes a private logical dump and restores to a NEW database in the same Neon Free project. It does not overwrite source data. The executed restore compared exact guest/session/review/preference/artifact rows. Private dump and logs remain ignored. This is not managed PITR or an executed production rollback. The retained restore database consumes the same free storage allowance; remove only after an explicit retention decision.

For rollback, keep protection enabled, stop sharing a failing preview, and use the previous verified immutable preview with schema1 compatibility. Redeploy its exact source SHA if needed; do not merge or force-push. Both Vercel builds use the same schema1; rollback does not recover deleted/expired guest data. To restore state, first restore into a new database, verify digests/rows/role permissions, then switch the restricted DSN and redeploy after review. Never run destructive restore over the online source. Reverting to pre-migration SQLite on Vercel is prohibited. No automatic destructive down migration exists.
